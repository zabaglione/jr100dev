# 別の生成 AI へ渡す制作指示書

次の指示を、SDK の場所と作りたい遊びに合わせて渡します。単に「ゲームを作って」だけで始めず、操作・成功・失敗・判断を含めると、完成条件を共有できます。

```text
この JR-100 SDK の Python 方式でゲームを完成させてください。
SDK: /path/to/jr100dev
作成先: games/my_first_game
ID: my-first-game
タイトル: （24 文字以内の大文字 ASCII）
遊び: （プレイヤーが繰り返し判断することを一文で）
操作: （WASD / 方向パッドと RETURN / ボタン）
成功条件: （画面で認識できる具体的な条件）
失敗条件: （危険、残量、時間など）
ROM: （所有する ROM のパス。なければ撮影は未確認として報告）
ローカル配置先: （指定がなければ build/release の生成まで）

最初に docs/python-games/README.md、language.md、testing.md を読むこと。
既存ゲームは変更しない。一般の Python と勘違いして import やクラスを使わない。

1. dev.py doctor で環境を確認する。
2. dev.py init で新規フォルダーを作り、GAME_DESIGN.md に判断・成功・失敗・面の展開を書く。
3. 雛形の初期状態を test し、合格してから企画のルール・絵・音・面へ変更する。
4. init/act/tick/draw の責任を守り、状態は s.name、配列は b/c/d を使う。
5. 小さな変更ごとに dev.py --json test を実行する。
6. 失敗したら error.code/file/line/hint と run.log を読み、ソースを修正して再実行する。
   エラーを隠す、期待値を実装に追従させる、失敗したステージを飛ばすことは禁止。
7. クリア、失敗、再挑戦、リセット確定と取消、境界の独立した期待値をリプレイに書く。
8. 一度遊べる状態になったら、目的・自分・危険・残量が初見で分かるかを確認する。
   長い操作説明はタイトルとヘルプにまとめ、本編は判断材料に集中させる。
9. dev.py release でビルド・テスト・撮影・配布物作成まで実行する。
   撮影は実 ROM と通常の入力だけを使い、クリアを作るための RAM 書き換えは禁止。
10. PNG を全て開き、文字切れ・重なり・見分けづらさを直す。MP4 を再生して入力と音を確認する。
11. ローカル配置先が指定されていれば --web-root を使い、HTTP 配信後に verify-published する。
12. PRG、元ソース、画像、動画、検証記録のパスと未確認事項を報告する。
    ビルド成功、エミュレーター成功、実機成功を混同しない。
```

## エラー修正の判断

JSON の `status` が `failed` なら未完了です。`error` を根拠に直します。修正箇所が DSL の対応外なら、未対応の API を作ったふりをせず、既存の API で表現できる構造に直します。難しさを理由にテストを消すことも、無関係の基盤を書き換えることも避けます。

失敗した独立期待値が正しいか分からない場合は、企画と操作を読み直します。例えば宝石が 2 個必要なのに 1 個で勝ててしまうなら、`s.gems` の期待値を 1 へ変えるのでなく、クリア条件を直します。企画を変える場合は企画・説明・テストを一緒に更新し、変更理由を残します。

## 完成の確認

実装量やファイル数は完成条件ではありません。短いプレイでも、選ぶ理由、反応、成功と失敗、もう一度試す導線を成立させます。テンプレートの宝石ゲームをそのまま別名にしたものを、依頼された別のゲームとして納品しないでください。

すべてを一度の依頼で進めることはできますが、生成 AI が企画の面白さまで自動で保証できるわけではありません。このキットは機械的な誤りを見つけ、修正と検証の結果を残すための土台です。遊びの評価と画面・音の目視確認は最後まで必要です。
