# テストと撮影

## 「動く」を 3 段階で確かめる

1. **検査とビルド**: 使用できる構文、引数、PCG 形式、コード領域と作業領域の上限を確認します。
2. **エミュレーターの操作テスト**: 生成した MB8861H コードにキー／パッド入力を送り、同じルールの Python モデルと状態・配列を比較します。さらに、作者が決めた期待値でクリア・失敗などを確認します。
3. **実 ROM の撮影確認**: 所有する ROM の BASIC から PRG を起動し、通常の入力でプレイします。画面と音を撮影して人が確認します。

2 の通常テストは合成 ROM を使うため、実 ROM を持っていなくても進められます。3 の公開用撮影では合成 ROM に代替しません。いずれもオリジナル JR-100 や SS1 の実機検証ではありません。

## tests/replay.json

各シナリオは新しく起動したゲームの最初の面から始まります。タイトルからの RETURN は自動で送ります。`demo` は動画撮影に使うシナリオ名です。

```json
{
  "schemaVersion": 1,
  "demo": "clear-first-stage",
  "scenarios": [
    {
      "name": "clear-first-stage",
      "steps": [
        {"expect": {"s.mode": 1, "s.player": 9}, "capture": "play"},
        {"press": "D", "repeat": 5, "expect": {"s.mode": 2, "s.gems": 2}, "capture": "clear"}
      ]
    }
  ]
}
```

| 項目 | 意味 |
| --- | --- |
| `press` | `W` / `S` / `A` / `D` / `RETURN` / `SPACE` |
| `repeat` | 同じ操作を 1〜255 回。期待値は最後の操作の後に確認 |
| `ticks` | `tick()` が進むのを 1〜255 回待つ。本編中だけ使用。`press` と同時には指定しない |
| `confirm` | SPACE のリセット確認や失敗後の RETURN の再挑戦に `true` / `false` で回答 |
| `expect` | `s.name`、`b[0]`、`c[3]`、`d[64]` などの期待値（0〜255） |
| `capture` | 撮影する PNG の名前。小文字・数字・ハイフン。拡張子不要。`title` は予約 |

シナリオは最低 1 個の期待値を必要とします。単に入力して落ちなかったという確認だけでは合格にしません。変数名の誤記、配列範囲、状態の不一致は `REPLAY` エラーとしてシナリオ名とステップ番号を返します。

`test` は各シナリオをキーボードとパッドで実行します。SPACE のリセット開始はキーボードで送ります。さらに 160 回の再現可能な混合入力で、通常移動、無効な移動、リセット、時刻更新、画面範囲、スタック、コードの破壊、タイトル音の PCM を確認します。これだけで全状態を網羅したことにはなりません。

## 必ず用意する経路

- 最初の面から全クリアまで。難しいゲームなら、各面の到達経路も分けて記録
- 失敗から再挑戦し、初期状態が戻ること
- リセットを取り消した場合と確定した場合
- 壁、端、残量 0、最後の 1 個などの境界
- 時間が進むゲームなら、入力なしでも時間切れなどが正しく起きること

期待値は企画から決めます。Python モデルと機械語は同じソースを使うため、両方に同じルールの誤りがあれば一致してしまいます。「5 回右へ進むと 2 個集まって面クリア」のような独立した期待値が、この穴を埋めます。新しい遊びに作り替えたら、雛形の経路だけを残さず、その遊びのテストに作り替えます。

数値演算のモデルは途中結果を 8 ビットに丸めます。`range(count)` の上限はループ中に変更しないでください。ネイティブ側は各周回で上限を読み直すため、通常の Python と相違が出ます。

## 動画用の入力を設計する

動画ではタイトルを見せ、操作の間に短い待ちを入れて、人が追える速度で再生します。最後は `s.mode` が 2 または 4 でなければ撮影を失敗扱いにします。`title.png` は自動撮影、ほかに最低 2 箇所の `capture` を指定します。動画は操作を省略せず、実時間の速度で 25 秒以上収録します。

実時間ゲームでは、入力間隔や撮影の待ち時間にもゲームが進みます。テストで成功しても `CAPTURE_REPLAY` で失敗したら、ゲームの猶予時間と経路を見直します。プレイヤーに不可能な高速入力を前提にしないでください。クリア状態を直接 RAM に書く方法は使いません。

撮影結果には PRG の SHA-256、ソースと SDK の指紋、入力時刻、撮影時刻、ホストからの状態書き換え回数（0 が必須）を記録します。動画にはエミュレーターから取り出した PCM を付け、ffprobe で映像・音声ストリームを検査します。ROM 本体やそのローカルパスは配布記録へ入れません。

## 失敗後のやり直し

`build/devkit/report.json` の `stage` と `error`、`run.log` を読みます。新しいビルドを開始すると以前のテスト・撮影の合格記録は無効になります。配布時にもソース・SDK・PRG・画像・動画のハッシュを照合します。

以前の `build/release/` が残っていても、それは前回の成果です。新しい `release` が `PASS` になるまで公開対象にしないでください。一般のゲームロジックを勝手に修正するコマンドはなく、作者または AI がソースを直して同じコマンドを再実行します。
