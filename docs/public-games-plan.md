# JR-100公開ゲームの候補と実装計画

作成日：2026-09-11

## 結論と対象

**JR-100・標準RAM 16KBで、第一陣6本、第二陣6本の計12本を開発候補とする。** 特にリアルタイム作品は負荷試作を通してから本制作へ進む。技術評価は設計上の見込みであり、12本の動作を確認済みという意味ではない。第一陣6本は実装済みで、標準16KBでの入力リプレイとWASM版の実BASIC経由起動を確認した。現行の作品・操作・実画面は[ゲーム一覧](../games/README.md)を参照。第二陣は引き続き開発候補である。Wikiと公開サイトへの反映は別の公開工程として扱う。

原案は、依頼者が会話に提供した「レトロPCで動くゲームアイディア100選」の全文を確認した。元の共有URLは https://share.gemini.google/3Wi8C81HhugC 。後半の「モダンな仕組みを重視する」という方向を採用する。前半100案、後半を重複整理した36系統、機種別の追加6案を[候補評価一覧](public-games-candidates.md)にまとめた。JR-800の画素描画を前提とした案は、そのままJR-100で実現できるとは扱わない。

要求は、独立した公開ゲーム、作り込んだタイトルロゴ・ゲーム画面・HUD、全作品の効果音、作品に合うBGM、Wikiの紹介と複数の実プレイ画像、保存済みBASIC ROMを使うWikiからのワンクリック起動。既存のローグライクや教材サンプルを新作数に数えない。

## 確認できた開発条件

- 標準16KB RAMを優先。MB8861Hの命令を使用し、コード・データ・作業領域・スタックを配置検査する。
- 画面は32列×24行、1文字8×8ドット。PCGは32文字。全面ビットマップや大量の独立した画像を前提にしない。
- キーボードと方向入力＋1ボタンで操作できる設計を基本とし、各作品で必要な操作を定める。
- 音は単音。効果音は必須とし、ゲームを止めない優先再生を共通基盤に実装する。BGMと効果音を同時発音できるとは扱わない。
- 現行RELIC DIVEには、入力・画面描画・ターン進行・迷宮生成・入力リプレイの実装がある。現在のソースを参照し、必要な部分だけを使う。
- `zabaglione/jr100dev` は公開リポジトリでWikiが有効。WikiのGit取得は `Repository not found` となり、既存ページは確認できていない。公開段階で初回ページの有無を確認する。

原案にあるVRAM `$0100-$03FF` は誤記。正しくは `$C100-$C3FF`。表示は256×192ドットだが、自由な全画面ビットマップとして扱わず、32×24セルとPCGの共有を前提に設計する。原案の「赤い警告」は、モノクロの輪郭・模様・段階的な形の変化へ置き換える。

根拠：[ハードウェアルール](../rules/hardware.md)、[命令の制約](../rules/assembly.md)、[サウンドドライバー](sound_driver.md)、[PCG Editor](../tools/pcg_editor/README.md)、[PCGアニメーション](../samples/pcg_animation/README.md)、[現行RELIC DIVE](../samples/relic_dive/README.md)。これらはソース・設定の確認であり、新作の動作試験や実機確認の結果ではない。

## ロゴ・画面・HUDの制作基準

装飾を最後に足すのではなく、各ゲームの**タイトル画面と代表的なプレイ画面を先にPCGで組む**。仮の記号画面のまま完成扱いにしない。外部の宣伝画像だけを豪華にして、実ゲームと違う印象を与えない。

- **タイトル**：大きな独自ロゴ、世界観が分かるキービジュアル、小さな動き、開始案内を入れる。ゲーム中とは別のPCGバンクを使える。タイトルの一画面内で使う固有字形は合計32個以内にし、ロゴと絵をそれぞれ32個と数えない。
- **画面遷移**：短いワイプ、模様の変化、数字の積上げなどを使う。スキップ可能にし、再挑戦は長いタイトル演出を経由しない。
- **キャラクター**：シルエットで敵味方・危険を判別できることを優先。2〜4枚の歩行／構え／命中フレームを同じPCGスロットに差し替える。共有コードを更新すると同じ字形を使う全員が変わる点を考慮する。
- **HUD**：体力、時間、敵の予告など判断に使うものを大きく配置。枠・アイコン・バー・警報を作品の世界観に合わせる。選択位置は輪郭や矢印でも示し、点滅だけに頼らない。
- **モノクロの描き分け**：白黒の面積、網目、輪郭、余白を使う。PCGとROM文字は併用できるが、PCG表示とROM反転表示は同一CMODEで併用できないため、反転属性を無条件に使うHUDにはしない。
- **画面予算**：1画面は必ず32×24セル。タイトルやHUDの配置データ、全アニメーションフレーム、圧縮前後の作業領域もRAM予算に含める。
- **制作データ**：PCG Editor／CRT Editorで編集可能な字形・配置データとASM資産を残す。ROMから取り出したフォントデータを公開資産へ混ぜない。

## 標準16KBの配分

以下は1作品の初期予算であり、実測値ではない。32KBへの拡張で超過を解決せず、まずコード・資産・同時オブジェクト数を調整する。

| 用途 | 初期予算（bytes） |
| --- | ---: |
| 下位領域・BASIC呼出し環境 `$0000-$02FF` | 768 |
| ゲームコード・共通コード・サウンド処理 | 6,144 |
| ロゴ・PCGバンク・アニメーション・画面配置 | 1,536 |
| ステージ・カード・短い英語説明 | 2,048 |
| 曲・効果音データ | 1,024 |
| ゲーム状態・描画用768バイト・展開作業領域 | 2,560 |
| 戻るための保存領域・I/O等の管理 | 768 |
| スタック | 512 |
| 調整用の空き | 1,024 |
| **合計** | **16,384** |

PCG実体の256バイトとVRAMの768バイトはこのRAM範囲外にあるが、RAM上に置く字形の元データや描画用バッファは上表に含む。コードサイズだけで「16KB対応」と判断しない。各予算の振替は可能だが、各状態の最大使用量・配置・スタック余裕をビルドと実行で検査する。

タイトル・プレイ・結果で排他的に使う作業領域は再利用できる。面データは必要に応じてRLEやビット詰めを用いる。カードや効果はIDと小さな表で持ち、効果ごとの長いコードや文章を増やさない。初版では電源断をまたぐ保存やブラウザー固有のセーブ機能を必須にしない。LOOP TENの持越しも同じプレイ中のRAM内だけで行う。

## 効果音・BGMと時間管理

既存の `SOUND_PLAY_SFX_BLOCKING` は同期的に待つため、そのままアクション中に呼ばない。新作共通の音声処理は既存の音高表とVIA設定を参照し、次を実装する。

1. 音イベントを登録し、定周期の短い更新で音高・長さを進める。入力待ち中も音だけは進む。
2. 単音の中で効果音をBGMより優先。効果音中もBGMの時刻は進め、終わった時点の音へ戻す。効果音の蓄積で古い発砲音が遅れて鳴らないようにする。
3. 優先順位は致命的な警報／被弾、重要な決定、攻撃、通常操作の順。連続する同種音は置換・間引きし、重大な音が失われないようにする。
4. Timer 1は単音出力、Timer 2の時間計数を周期管理の候補とする。ACRなど共有レジスタのビットを保護し、キーボード・PCGと同時に動くことを確認する。
5. 音と入力の更新は60Hz、リアルタイムのゲーム進行は原則30Hzを目標にする。894kHzでは約14,900サイクル／音更新、29,800サイクル／ゲーム更新が総予算。長い処理は分割し、実測で周期を越えないことを確認する。

固定クロックで10秒を計測し、描画負荷や無入力で伸びないことを確認する。音や判定に使う周期は、単なる可変長ループの呼出し回数と混同しない。実機上のタイマー精度と聴感は、エミュレーター試験とは別に記録する。

全作品に決定・取り消し・失敗・成功と固有の効果音を用意する。BGMはタイトル・選択・戦闘・結果など必要な場面へ限定し、音の変化点を記録して1KiB程度の音データを目安に作る。ABYSS SIGNALではソナーと警報の意味を優先し、常時BGMを付けない。既存曲の流用を前提とせず、短い独自フレーズを作る。

## 配置と開発順序

新作は `games/<game-id>/` に置き、教材用の `samples/` と分ける。各作品にソース、ビルド手順、操作説明、ライセンス、必要な検証コードを揃える。生成物は `build/` に出力する。

共通処理は、入力、文字・PCG描画、乱数、時間管理、停止しない音声処理など、複数作品で実際に必要なものを `games/common/` にまとめる。タイトル・HUDの画面資産は作品ごとに持つ。ビルド定義はサンプルのディレクトリ構造に依存させず、公開ゲームをまとめてビルドできる `make games` を用意する。

1. **共通基盤とCHRONO BREACHの画面を作る**：タイトルと1面をPCGで制作。操作、停止しない効果音、定周期更新、RAM配置を確認する。
2. **CHRONO BREACHを完成させる**：20面、演出、再挑戦、説明、入力リプレイを揃える。完成したPRGと実フレームを公開候補にする。
3. **エミュレーターの起動リンクを実装する**：そのPRGで保存済みROMからタイトルまでの自動起動を検証する。これは第一陣の最初から行う。
4. **最初のWiki公開を通す**：メール非公開設定、noreply、公開範囲の確認後、作品ページ・実プレイ画像・起動リンクを公開し、公開URLから動作を確認する。
5. **第一陣の残り5本を順に完成・掲載する**：各作品で画面、遊び、音、検証、Wikiまで揃える。一度に未完成品を増やさない。
6. **第二陣へ進む**：共通部分を使いつつ、工場・サバイバーなどの負荷試作を行う。採用基準に達した作品を順次追加する。

## 完成と検証の基準

- **静的・ビルド確認**：使用命令、分岐範囲、16KB内の配置、スタックとの非重複、PCG 32文字以内、配布PRGとビルド結果の一致を確認する。ツールチェーンを変更した場合は関連する既存テストも実行する。
- **エミュレーターでの実行確認**：配布するPRGを使い、起動、キーボード・パッド操作、主要なルール、勝敗、再挑戦を確認する。作品に応じて入力リプレイやマップの到達性検査を用いる。リアルタイム作品は更新速度・入力反応・音による停止も計測する。
- **画像確認**：配布PRGの実際の描画フレームからタイトル1枚、象徴的なプレイ場面2〜3枚、必要に応じてクリア場面を取得する。VRAMの文字ダンプだけでなく、ROM文字・PCGが合成されたフレームを見る。文字・選択位置・端部の見切れを確認し、整数倍拡大と余白で読みやすくする。画像に短い場面説明を付ける。計画用のイメージ図を実プレイ画像として掲載しない。
- **実機確認**：上記とは別に記録する。実機で試していない作品には「エミュレーター確認済み／実機未確認」と明記する。ビルド成功を実機動作の証拠にはしない。

## Wikiの構成と公開条件

一覧ページに各ゲームのタイトル、短い概要、タイトル画像、個別ページへのリンクを掲載する。個別ページには次を揃える。

- ゲームタイトル、概要、目的・クリア条件
- 対応メモリ容量、操作表、始め方
- タイトル画面と複数の代表的なゲーム中画面、場面説明
- 確認したバージョンとエミュレーター／実機の確認状況
- 保存済みROMを使う「プレイ」リンクと、ビルド可能なソース・手順へのリンク
- ライセンスと必要な出典

公開前にGitHubの **Keep my email addresses private** を確認・設定する。Wikiの初回ページをWebで作成する場合も、この設定を先に行う。ソース用とWiki用の両Gitリポジトリには、GitHubが提供するnoreplyアドレスを設定し、新しく公開するコミットのauthor・committerを確認する。現在の `jr100dev` の有効なGitメール設定はnoreplyではなく、この段階では未変更。

新規ゲームの画像・音・文章は公開可能な自作素材を基本とし、既存コードを使う場合は該当ライセンスと表示義務を確認する。RELIC DIVEのMIT表示をリポジトリ全体のライセンスと解釈しない。公開候補ファイルを限定し、ROM、私的資料、個人情報をソース・Wiki・配布物に含めない。

Wikiは独立したGitリポジトリとして更新する。初回ページが存在しなければGitHub上で作成後に取得する。画像はWiki側で管理し、公開後に一覧・個別ページ・画像・起動・ソースリンクを確認する。GitHubのWeb操作で作られる初回コミットと、その後のローカルGitからのコミットの両方がnoreplyになっていることを確認する。

公式資料：[Wikiページの作成とローカル編集](https://docs.github.com/en/communities/documenting-your-project-with-wikis/adding-or-editing-wiki-pages)、[コミット用メールと非公開設定](https://docs.github.com/en/account-and-profile/how-tos/email-preferences/setting-your-commit-email-address)。

## Wikiからのワンクリック起動

**第一陣の対応範囲に含め、ローカルのエミュレーターへ実装済み。保存ROMを使う起動をブラウザーで確認し、6本のWASM起動も検証した。公開サイトへの反映は未完了。** 利用者は同じブラウザーの既存エミュレーターへBASIC ROMを事前登録済み、という条件にする。

現行の [JR-100 Web Emulator](https://zabaglione.github.io/pyjr100emu/) の `web/storage.js`・`web/emulator.js` には、IndexedDBへ保存したROMの自動復元がある。`cpp/src/core.cpp` は、`entry=$0300` などの入口を持つPRGを読み込み、`A=USR($0300)` の入力を自動で予約できる。今回、この既存経路へゲーム選択・取得・起動順序の管理を加えた。

提案中のURL仕様は `https://zabaglione.github.io/pyjr100emu/?game=chrono-breach`。**この例は現在機能する起動リンクではない。** Wiki内にエミュレーターを埋め込まず、通常のリンクで既存サイトへ移動する。

```text
Wikiの「プレイ」を1回クリック
  → 既存エミュレーターへ移動し、game IDをカタログに照合
  → 保存済みBASIC ROMを復元し、WASMコアの準備完了を待つ
  → 16KBモードで起動し、カタログ指定のゲームPRGを取得・検証
  → PRG読込と既存の自動USR実行
  → ゲームのタイトル画面、キーボード／パッドで操作可能
```

ゲームの「タイトルからスタート」はゲーム内の操作として残す。ROM再選択、手動ダウンロード、PRG選択、USR入力、エミュレーターの追加Runボタンは不要にする。保存設定が32KBでもカタログの `ramKiB: 16` に従ってゲーム起動時は16KBにし、必要なら次の通常起動用の設定とは分ける。

ROMは配布・アップロードせず、利用者のブラウザー内で扱う。IndexedDBはオリジンごとの保存なので、Wikiの `github.com` からROMを読むのではなく、保存済みの `zabaglione.github.io` の既存アプリと同じデータベースを使う。別ブラウザー、プライベートブラウズ、サイトデータ削除後などでROMがない場合は自動起動を中止し、事前設定が必要なことを表示する。[IndexedDBの保存範囲](https://developer.mozilla.org/en-US/docs/Web/API/IndexedDB_API)

PRGとカタログは既存エミュレーターのPagesから同一オリジンで配信する。`jr100dev` の公開用ビルドで生成したゲームだけを、版とSHA-256を確認してエミュレーターの配布物へ取り込む。カタログにはID、タイトル、版、PRGの相対パス、開始アドレス、必要RAM、SHA-256、ソースURLを持たせる。任意の外部URL・ローカルパス・開始アドレスをURL引数から実行する方式にはしない。

| 対象 | 実装する内容 |
| --- | --- |
| `jr100dev/games/` とビルド処理 | ROMを含まないPRG、開始アドレス、カタログ、検証済み画像とWiki原稿の出力 |
| `pyjr100emu/web/` の起動処理 | ID解析、カタログ取得、保存ROM・コア・PRGの準備順序、16KB指定、重複起動防止、エラー表示 |
| `pyjr100emu/tools/build_web.py` 等 | 公開ゲームとカタログをPages配布物へ含め、版・ハッシュ・ROM非同梱を検査 |
| `pyjr100emu/web/tests/` | IDと異常系の検査、ROM保存済みからのブラウザー起動確認 |
| `jr100dev.wiki` | 一覧、ゲーム別ページ、タイトルと代表場面の画像、「プレイ」とソースリンク |

既存のC++ PRGローダーと自動実行を利用する方針で、ゲーム選択のためにCPU実装を増やす必要はない。ROM読込直後の起動順序や入力予約に問題が見つかった場合だけ、その経路を修正する。ゲーム・カタログを配信してから、その版に対応するWikiリンクを掲載する。

受入条件は「ROMを登録済みの同じブラウザーで、実際のWikiのリンクを1回クリックし、ファイル選択や手動USR入力なしに指定ゲームのタイトルが出て操作できる」こと。最初の作品で公開環境まで確認し、以後は各作品のカタログとPRGを追加する。

さらにROM未保存、未知のID、再読込、PRG取得失敗、ハッシュ不一致、32KB設定が残っている場合、入力の押し残しを確認する。ROMを必要とする受入試験はローカルの所有ROMで行い、公開CIへ実ROMを置かない。

**画面の自動起動と音声の自動開始は別条件。** ブラウザーによってはページ移動後の音声が制限される。ゲームは自動起動し、最初の決定キー／画面操作で音声を有効にする。Wikiのクリックだけで必ずタイトルBGMまで鳴るとは保証せず、ゲームパッドのみの場合も含め実際に確認する。[Web Audioの自動再生制限](https://developer.mozilla.org/en-US/docs/Web/Media/Guides/Autoplay)

公開環境で起動を確認できない場合だけ、元の依頼どおりソースリンクを代替として掲載し、起動リンク対応は未完了と報告する。技術的な障害がない限り、最初からワンクリック起動を完成させる計画とする。
